# 开发实现基线

## 1. 文件定位

- 本文件用于约束 Han 代码、脚本、配置、SQL 和文档改动的基本工程质量。
- 任何进入实现阶段的任务，都应读取本文件。

## 2. 改动前检查

- 先阅读相关代码、测试、配置、文档，再动手。
- 先确认本次改动不会破坏现有功能、接口、数据格式、兼容行为。
- 先列出本次改动影响的模块、接口、配置项、脚本、SQL、文档和发布对象。
- 高风险改动先考虑备份点、特性开关或回滚点。

## 3. Han 技术栈约束

- 后端以 Java 21、Spring Boot、Spring Cloud、Maven 为主。
- 前端以 Vue 3、TypeScript、Vite 为主。
- 数据库以 PostgreSQL 为正式主库。
- 服务治理和配置以 Nacos 正式口径为准。
- 未经确认，不新增替代主技术栈或平行架构。

## 4. 后端实现要求

- 已有系统能力必须优先复用，禁止绕开字典、模型管理、Prompt 模板、文件、异步任务、权限、租户、配置、审计、用量统计等模块另写平行能力。
- 新增枚举、模型类型、模板分类、状态、策略或配置项时，优先进入对应字典、配置、模板或模型管理模块；如需人工录入，交付时必须给出可直接录入的数据清单。
- JSON 处理优先使用 Jackson，禁止新增 Gson、Fastjson、Fastjson2。
- 服务间调用优先使用 `@HttpExchange` 声明式客户端，禁止新增 Feign。
- 对象转换优先使用 MapStruct 或 Converter 层收口。
- 不把第三方工具 API 直接散在业务层。
- 保持错误处理、边界处理、恢复逻辑明确。
- 公共 API、公共类、公共函数应有必要文档或注释。
- 修改公共模块时必须保持公共扩展性，通过通用 DTO、Service、Client、Converter、组件或工具函数封装复用能力，保证其他模块可以公共调用。
- 公共模块不得只为单一业务场景硬改；业务私有规则应留在对应业务编排层，公共模块保留兼容入口、默认行为和错误边界。

## 5. A/I/B 分层要求

- B 层承载通用业务流转，不标 `@RestController`。
- A 层面向管理端接口，必须显式权限控制。
- I 层面向内部服务调用，必须显式内部鉴权。
- A/I 层控制器应使用唯一 Bean 名称，避免冲突。
- 兼容现有路由优先于强行统一前缀。

## 6. 前端实现要求

- 不为了视觉调整破坏当前业务链路、权限判断、运行时能力降级逻辑。
- 页面级可见不等于功能级可用，必须关注接口错误、业务错误和控制台错误。
- 涉及 `small / medium / full` 能力差异时，优先读取运行时能力接口，不写死假能力。
- 不提交 `han-ui/dist`、`node_modules`、Playwright 输出目录。

## 7. SQL 与配置实现要求

- SQL 初始化只认 `sql/tiers/{small,medium,full}`。
- PostgreSQL 升级脚本只进入 `sql/upgrades/postgres/`。
- Nacos 导入脚本与 tier 初始化脚本保持同档同步。
- secrets 不写入 Git。
- 修改配置时必须说明环境、配置项、默认值、兼容影响和回滚方式。

## 8. 命名与编码

- 命名遵循对应语言惯例。
- 正文内容默认中文。
- 路径名和规则资产文件名优先使用稳定 ASCII 命名，避免路径兼容问题。
- 新增或重写文档统一使用 UTF-8 编码。

## 9. 禁止事项

- 不做与当前目标无关的大重构、大搬家、大面积格式化。
- 不引入魔法数字、硬编码密钥、不可追踪常量。
- 不只修表面症状，不修根因链路。
- 未确认具体技术栈前，不臆造框架、构建工具、运行时或部署链路。
- 新增依赖前必须确认已有依赖管理方式、锁文件、版本范围和兼容性。
