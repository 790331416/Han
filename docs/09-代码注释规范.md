# Han 代码注释规范

## 1. 目标

本规范用于统一 Han 前后端代码注释口径，保证公共模块、业务模块和 AIVideo 扩展模块都能做到：

- 注释解释“为什么这样做”“边界是什么”“会影响哪里”，而不是机械复述代码；
- 注释全部使用中文，编码统一为 UTF-8，不允许乱码、错码或不可读文本；
- 公共模块优先补齐注释，保证其他模块接入时能看懂、能复用、能扩展；
- 注释与代码保持同步，代码变了必须同步更新注释。

## 2. 总体原则

### 2.1 必须注释的场景

- 公共类、公共接口、公共方法。
- 跨模块复用的工具类、组件、组合式函数、字典加载器、基础配置加载器。
- 复杂业务分支、兜底逻辑、兼容逻辑、缓存逻辑、租户逻辑。
- 容易误用的参数约束、返回值约束、幂等要求、回滚要求。
- 与数据库初始化、升级脚本、运行期兜底三套来源一致性相关的代码。

### 2.2 不应该写的注释

- 纯复述代码表面行为的注释。
- 已经失效、和实际逻辑不一致的注释。
- “临时改一下”“先这么写”但没有上下文的注释。
- 大段无结构说明、无法指导维护的流水账注释。

### 2.3 注释优先级

1. 公共基础模块。
2. 跨模块共享组件或工具。
3. 复杂业务入口。
4. 普通业务页或简单 CRUD。

## 3. 后端注释规则

### 3.1 JavaDoc 适用范围

以下对象必须补 JavaDoc：

- `public class`
- `public interface`
- `public enum`
- `public record`
- `public` / `protected` 方法

推荐格式：

```java
/**
 * 字典运行期兜底注册中心。
 *
 * <p>负责在租户首次访问字典接口时补齐内置字典，保证数据库初始化、
 * SQL 升级脚本和运行期兜底三套来源保持一致。
 */
public class SysBuiltinDictRegistry {

    /**
     * 为当前租户补齐缺失的内置字典。
     *
     * @throws RuntimeException 当数据库写入失败时回滚当前事务
     */
    public void ensureBuiltInDictionaries() {
    }
}
```

### 3.2 控制器与开放接口

- Controller 类要说明“是谁调用、负责什么、不负责什么”。
- 对外接口方法要说明查询条件、幂等性、是否包含运行期兜底逻辑。
- 推荐同时补 `@Tag`、`@Operation`、`@Parameter` 等 OpenAPI 注解，注解描述统一中文。

### 3.3 私有方法与复杂逻辑

以下情况必须补块注释或方法注释：

- 多租户判定。
- 运行期兜底或回退。
- 兼容旧数据、旧模板、旧参数的逻辑。
- 复杂 SQL 组装、复杂查询条件。
- 容易被误删的保护判断。

示例：

```java
/**
 * 统一把空租户视为平台租户，避免运行期插入 null 租户脏数据。
 */
private Long resolveTenantId() {
    Long tenantId = TenantHelper.getTenantId();
    return tenantId != null ? tenantId : 0L;
}
```

## 4. 前端注释规则

### 4.1 Vue 页面

以下内容建议补注释：

- 页面职责说明。
- 组合式状态来源。
- 公共字典、公共配置、回退策略的加载逻辑。
- 流式任务、轮询、媒体预览、跨阶段状态同步。

示例：

```ts
/**
 * 页面不直接维护写死的状态枚举，统一走 `han-ui/src/utils/dict-options.ts` 的
 * 公共字典加载，这样列表页、表单页和详情页可以共享同一套来源。
 */
const { statusOptions, modelTypeOptions } = await loadDictOptionSet({
  statusOptions: { dictType: SYS_NORMAL_DISABLE_DICT },
  modelTypeOptions: { dictType: AI_MODEL_TYPE_DICT }
})
```

### 4.2 TypeScript 工具与组合式函数

公共工具必须写清楚：

- 输入输出约束。
- 失败时是否回退。
- 是否允许空值。
- 为什么放在公共层，而不是业务页里临时实现。

示例：

```ts
/**
 * 根据字典值查找展示标签。
 *
 * <p>统一收敛页面里的 find(...)?label 逻辑，避免每个页面重复维护。
 */
export function findDictLabel(options: DictOption[] = [], value?: string, emptyText = ''): string {
  return options.find((item) => item.value === value)?.label || value || emptyText
}
```

### 4.3 模板层

- 模板层尽量少写注释，避免干扰阅读。
- 只有结构复杂、条件渲染层级深、存在强业务约束时，才补简短注释。
- 模板注释不能替代脚本层注释。

## 5. SQL 与脚本注释规则

- 初始化 SQL、升级 SQL、回填 SQL 必须标明用途和适用范围。
- 新增字典、配置、模板时，要说明“初始化”“升级补齐”“运行期兜底”三者关系。
- 部署脚本、验证脚本要说明依赖环境、输入参数、回滚方式或失败处理策略。

示例：

```sql
-- AIVideo 扩展字典：素材访问策略
-- 说明：用于项目基础配置、设置页和后续媒体权限控制统一下拉来源
```

## 6. 编写要求

### 6.1 语言与格式

- 注释统一中文。
- 段落说明推荐使用 `/** ... */`。
- 单行补充说明可使用 `//`。
- 不允许混用乱码、拼音缩写、不可读英文碎片。

### 6.2 内容要求

每条有效注释至少回答下列问题之一：

- 这段逻辑的业务目的是什么？
- 为什么不能直接简化？
- 这里在兼容什么旧行为？
- 这里的边界条件是什么？
- 这里和哪些公共模块、配置、字典、SQL 有联动？

## 7. 注释落地顺序

当前仓库建议按下面顺序持续补齐：

1. `han-common`、`han-modules`、`han-ui/src/utils` 等公共层。
2. AI / AIVideo 公共配置、字典、模板、工作流、媒体链路。
3. 复杂工作台页面和流式生成页面。
4. 其他普通管理页。

## 8. 检查清单

提交前至少确认：

- 公共模块新增或改动的方法是否补了中文注释。
- 注释是否仍然和代码一致。
- 是否把“兜底来源”“字典来源”“配置来源”写清楚。
- 是否出现复述式废话注释。
- 是否引入乱码或错误编码。

## 9. 与系统能力的关系

- 系统已经有字典、配置、模板、模型等公共能力时，优先复用系统能力，并在注释中说明复用点。
- 如果因为兼容性或迁移阶段保留了本地 fallback，必须在注释里写明 fallback 的目的和移除条件。
- 修改公共模块时，必须保持可扩展、可复用、可封装，避免把 AIVideo 私有逻辑硬编码进系统公共层。
