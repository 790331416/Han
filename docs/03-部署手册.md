## 1. 部署方案选择

### 1.1 三档部署对比

| 档位 | 适用场景 | 建议资源 | 默认能力 | 正式部署入口 |
| --- | --- | --- | --- | --- |
| `small` | 本地开发、演示、核心链路验证 | 2 核 4GB | 核心后台、通知、任务调度、监控 | `deploy/small/docker-compose.yml` |
| `medium` | 团队联调、标准测试环境 | 4 核 8GB | `small` + 租户、工作流、开放平台、文件服务 | `deploy/medium/docker-compose.yml` |
| `full` | 完整业务联调、AI 联调、发布预演 | 8 核 16GB+ | `medium` + AI、AI 短剧与代码生成 | `deploy/full/docker-compose.yml` |

### 1.2 正式入口

- `small`：`deploy/small/docker-compose.yml`
- `medium`：`deploy/medium/docker-compose.yml`
- `full`：`deploy/full/docker-compose.yml`

禁止继续把根目录历史 `docker-compose*.yml` 作为长期正式部署入口。

## 2. 通用部署前检查

### 2.1 必查文件

- 对应 tier 的 `deploy/<tier>/docker-compose.yml`
- 对应 tier 的 `.env`
- 对应 tier 的 PostgreSQL 初始化 SQL
- 对应 tier 的 Nacos 导入 SQL

### 2.2 必查变量

- `HAN_DEPLOY_TIER`
- `HAN_INNER_AUTH_SECRET`
- 数据库连接信息
- Redis 连接信息
- Nacos 连接信息
- AI Provider 密钥
- 对象存储和消息队列连接信息

### 2.3 初始化规则

- PostgreSQL 初始化只认 `sql/tiers/<tier>/<tier>-init.sql`
- Nacos 导入只认 `sql/tiers/<tier>/<tier>-nacos-derby-import.sql`
- 增量升级只认 `sql/upgrades/postgres/`

## 5.6 AIVideo full 正式部署

AIVideo 当前属于 `full` 档正式能力，不新增第四档 tier。`ui` 服务在 full 环境默认使用独立创作端镜像 `han-aivideo-ui`，同时承载 `/studio/**` 创作页面和 `/ai/aivideo/**` 管理页面；通用后台 `han-ui` 仍作为独立通用产品镜像维护，不与短剧发布产物混用。

正式发布链路固定为：

```text
feature/aivideo-* 隔离实现与验证
  -> 合并 master
  -> GitHub Actions 测试、构建
  -> ACR 推送不可变 commit tag
  -> 95 /opt/han/deploy/full 拉取镜像
  -> PostgreSQL 演练、服务探针、接口与浏览器回归
```

发布边界：

- `master` 是 95 唯一正式发布来源；临时分支只能生成候选 commit tag，不得直接作为 95 正式版本。
- 后端和前端镜像只能由 GitHub Actions 构建；95 不执行 Maven、pnpm 或 `docker build`。
- `.github/workflows/aivideo-image.yml` 负责测试并构建 `han-ai`、`han-aivideo`、`han-aivideo-ui`。
- `.github/workflows/full-app-image.yml` 负责受影响的 full 通用服务与 `han-aivideo-ui`。
- 每次构建必须推送 `<commit短SHA>` 不可变 tag 并检查远端 manifest；`latest` 只作便利指针，不作为精确发布或回滚依据。
- SQL-only 变更不会因为不在 workflow `paths` 中而自动触发业务镜像构建；这类变更必须执行 PostgreSQL 演练和数据库升级门禁，不能把“没有新镜像”误判为 CI 失败。
- 服务器 `.env`、模型密钥、数据库密码、令牌和镜像仓库凭据不得进入 Git、普通文档或测试输出。

full 关键镜像变量：

| 服务 | 环境变量 | 镜像 |
| --- | --- | --- |
| AI 通用能力 | `HAN_AI_IMAGE` | `han-ai:<commit短SHA>` |
| AIVideo 后端 | `HAN_AIVIDEO_IMAGE` | `han-aivideo:<commit短SHA>` |
| AIVideo 独立 UI | `HAN_UI_IMAGE` | `han-aivideo-ui:<commit短SHA>` |
| 网关等通用服务 | 对应 `HAN_*_IMAGE` | 仅在本轮改动影响时升级 |

媒体运行边界：

- full 文件服务默认 `HAN_FILE_MAX_FILE_SIZE=300MB`、`HAN_FILE_MAX_REQUEST_SIZE=320MB`。
- 独立 UI、外层反向代理和网关的请求体上限必须不低于目标媒体大小；任一层更小都会成为实际上传上限。
- 供应商视频已生成但下载、归档或查询遇到临时错误时，`han-aivideo` 必须保留供应商任务 ID 并支持刷新恢复，避免重复生成和重复计费。

GitHub Actions 访问 ACR 需要受控的 `ACR_USERNAME`、`ACR_PASSWORD` Secrets；凭据只进入 GitHub Secrets，不进入仓库文件和普通日志。

95 拉取部署示例：

```powershell
. D:\code\Han\scripts\helpers\use-d-drive-dev-env.ps1
D:\code\Han\scripts\helpers\deploy-aivideo-acr.ps1 `
  -Tag <master短SHA> `
  -Services gateway,ai,aivideo,ui `
  -SshTarget root@10.18.35.95 `
  -DeployDir /opt/han/deploy/full
```

该脚本只检查 ACR manifest、备份 `.env`、更新镜像变量、执行 `docker compose pull/up` 和健康检查，不在服务器构建镜像。服务列表必须按最终差异确定，不能固定升级未受影响服务。

部署后至少执行：

```bash
cd /opt/han/repo/Han
bash deploy/scripts/rehearse-postgres-upgrades.sh
bash deploy/scripts/rehearse-postgres-backup-upgrades.sh --from-compose-tier full
bash deploy/scripts/verify-95.sh full
bash deploy/scripts/verify-file-service-95.sh full
```

随后按 `docs/04-测试与验收手册.md` 执行 full 接口矩阵和 AIVideo 真实浏览器同会话回归。历史双机 `full-lite` 方案只保留在 `D:\code\AIVideo\docs\开发计划\Han-AIVideo双机部署设计.md` 作为阶段资料，不再覆盖本节正式口径。

## 6. 本地开发环境部署

本节吸收了历史部署文档中的本地开发内容，但路径和初始化入口改为当前正式结构。

### 6.1 仅启动中间件

本地联调时，只启动中间件和必要依赖，不建议再维护一套独立旧脚本。

### 6.2 本地初始化顺序

1. 导入对应 tier 的 PostgreSQL SQL
2. 导入对应 tier 的 Nacos SQL 或按正式模板创建配置
3. 启动网关、认证、系统及所需业务模块

### 6.3 Nacos 说明

- JobFlow 相关配置已并入各 tier Nacos 导入 SQL
- 本地如果不直接导 SQL，应至少补齐正式手册中要求的配置项

## 9. 备份、回滚与升级

### 9.1 PostgreSQL

- 发布前建议做逻辑备份
- 发布后如有结构变更，记录已执行的升级脚本
- 备份恢复型升级演练：
  - `deploy/scripts/rehearse-postgres-backup-upgrades.sh --from-compose-tier full`
  - `deploy/scripts/rehearse-postgres-backup-upgrades.sh --backup /path/to/backup.sql`
- 该演练只使用临时 PostgreSQL 容器，不得直接在 `/opt/han/deploy/{small,medium,full}` 运行库上重放升级脚本

### 9.2 Nacos

- 导入前备份 Derby 数据目录或当前配置
- 变更后记录导入的脚本版本

### 9.3 回滚

1. 确认上一个已验证的 `master` 提交、不可变镜像 tag 或 digest。
2. 使用部署脚本生成的 `.env.bak-<tag>-<timestamp>-deploy-script` 恢复镜像变量，或显式改回上一个已验证 tag/digest。
3. 在 `/opt/han/deploy/<tier>` 执行目标服务的 `docker compose pull` 和 `docker compose up -d --no-deps --force-recreate`。
4. 重新执行对应 tier 验证、专项探针、接口矩阵和浏览器回归。
5. 数据库变更不能只靠镜像回滚；必须按升级脚本的兼容设计和发布前备份单独判断数据回滚方案。

### 9.4 GitHub Actions、ACR 与 95 拉取验证

正式镜像必须由 `master` 对应的 GitHub Actions run 构建并推送到 ACR。发布前逐项确认：

- workflow 中测试、构建、推送和远端 manifest 检查全部成功。
- 目标镜像存在 `<commit短SHA>` 不可变 tag，且来源提交与待发布 `master` HEAD 一致。
- 95 只从 `/opt/han/deploy/{small,medium,full}` 拉取和重建服务，不执行本地打包或镜像构建。
- 发布服务清单由最终差异决定；未受影响服务不得无理由一起升级。
- `latest` 不作为回滚依据，回滚使用已验证 commit tag 或 `repo@sha256:<digest>`。

AIVideo 可使用受控部署助手：

```powershell
D:\code\Han\scripts\helpers\deploy-aivideo-acr.ps1 `
  -Tag <master短SHA> `
  -Services <受影响服务> `
  -SshTarget root@10.18.35.95 `
  -DeployDir /opt/han/deploy/full
```
部署助手默认只接受当前 `origin/master` 的 7 位或完整 commit tag。`-AllowNonMasterTag` 只用于显式指定的隔离非生产主机，脚本会拒绝用该开关把非 master tag 部署到默认 95。
其他服务从 95 对应 tier 执行：

```bash
docker compose pull <service>
docker compose up -d --no-deps --force-recreate <service>
docker compose ps <service>
```

如需固化 digest，可在目标 tag 的所有远端 manifest 已存在后生成发布清单：

```bash
deploy/scripts/generate-image-release-manifest-95.sh \
  --tag <commit短SHA> \
  --source-commit <master完整commit> \
  --services <服务列表> \
  --output deploy/release-manifests/<release-tag>.env
```

发布清单只允许记录镜像地址、来源提交、服务列表和 digest，不得包含仓库凭据、服务器密码、数据库密码或令牌。`deploy/scripts/publish-service-images-95.sh` 不属于当前 GitHub Actions 正式发布链路，不得用它替代 CI 构建。

拉取完成后必须验证容器状态、健康检查、关键接口、错误路径和页面行为；只看到 `docker compose up` 返回成功不能判定发布完成。

## 10. 故障排查

本节吸收了历史部署文档中的常见排障内容，并按当前正式结构简化。

### 10.1 推荐排障顺序

1. PostgreSQL
2. Redis
3. Nacos
4. Gateway
5. 核心业务服务
6. UI
7. 页面级健康回归

### 10.2 常见问题

- 服务启动失败
  - 先看容器日志
  - 再看环境变量与连接信息
- Nacos 注册或配置未生效
  - 先确认 Nacos 是否活着
  - 再确认配置是否真的导入到当前 tier
- 数据库连接失败
  - 检查数据库实例、库名、用户、密码
- 页面能开但里面报 404 / 500
  - 先跑页面级健康回归
  - 再查服务日志与运行时能力

## 11. 禁止项

- 不再使用根目录旧 compose 作为长期正式入口
- 不得手工上传 `jar`、`dist`
- 不得依赖历史构建产物做发布
- 不得把 secrets 写入 Git
- 不得在 95 上继续沿用历史临时发布目录
