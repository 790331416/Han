# 仓库整理与重构执行计划

## 1. 计划定位

本文档是 Han 仓库后续整理的唯一主计划。

后续所有整理动作都以本计划为准，目标不是继续把仓库拆成大量碎文档，而是参考若依文档的组织方式，收敛为：

- 一个大 README
- 少量正式大手册
- 一份总规则文档
- 每档一个大 SQL
- 一套正式部署入口

本计划同时覆盖仓库结构、文档结构、SQL 结构、规则结构、95 环境结构和最终验收标准。

## 2. 参考口径

本计划参考了若依的文档与仓库组织方式：

- 分离版文档入口：[RuoYi 文档](https://doc.ruoyi.vip/ruoyi/)
- 微服务版文档入口：[RuoYi-Cloud 文档](https://doc.ruoyi.vip/ruoyi-cloud/)
- 微服务版仓库：[RuoYi-Cloud 仓库](https://gitee.com/y_project/RuoYi-Cloud)

参考后的结论是：

- README 应该承担项目介绍、能力说明、快速开始和文档导航，不应退化成只有链接的索引页
- 正式文档应按“大类手册”组织，而不是拆成很多治理小文档
- 微服务专题可以单独成章节，但仍应收敛在少量大手册中
- SQL 入口应简洁直接，初始化脚本不应过度碎片化
- 历史资料应归档，不应继续占用正式入口

## 3. 最终目标

### 3.1 README 目标

`README.md` 恢复并固定为项目大入口，内容至少包括：

- 项目简介
- 核心特性
- 架构设计
- 技术栈
- 项目结构
- 三档部署矩阵
- 快速开始
- 文档导航
- SQL 与部署入口说明
- 开发与测试入口说明

README 不再只做“目录跳板”，而是回到你当前认可的“大而全”风格。

### 3.2 正式文档目标

正式文档不再维持当前偏碎的目录树，最终收敛为以下几份大文档：

```text
docs/
├─ index.md
├─ 01-产品与架构总览.md
├─ 02-开发手册.md
├─ 03-部署手册.md
├─ 04-测试与验收手册.md
├─ 05-运维与95环境手册.md
├─ 06-牛马协作总规则.md
├─ 07-仓库整理与重构执行计划.md
└─ archive/
```

说明：

- `index.md` 只做正式文档索引
- 正式文档控制在 7 份左右，不再细分一堆治理、部署、测试碎文件
- 历史报告、分析、流程图、临时纪要统一进入 `archive/`

### 3.3 SQL 目标

SQL 最终改成“每档一个大初始化 SQL”，不再按 `system/job/...` 拆目录。

```text
sql/
├─ README.md
├─ tiers/
│  ├─ small/
│  │  ├─ README.md
│  │  ├─ small-init.sql
│  │  └─ small-nacos-derby-import.sql
│  ├─ medium/
│  │  ├─ README.md
│  │  ├─ medium-init.sql
│  │  └─ medium-nacos-derby-import.sql
│  └─ full/
│     ├─ README.md
│     ├─ full-init.sql
│     └─ full-nacos-derby-import.sql
├─ upgrades/
│  └─ postgres/
└─ archive/
```

写法规则：

- `small-init.sql` 内部用注释分段：
  - `-- system`
  - `-- job`
- `medium-init.sql` 内部用注释分段：
  - `-- system`
  - `-- job`
  - `-- tenant`
  - `-- workflow`
  - `-- open`
  - `-- file`
- `full-init.sql` 内部用注释分段：
  - `-- system`
  - `-- job`
  - `-- tenant`
  - `-- workflow`
  - `-- open`
  - `-- file`
  - `-- ai`
  - `-- gen`

原则：

- 初始化只认 `tiers/<tier>/<tier>-init.sql`
- Nacos 导入只认 `tiers/<tier>/<tier>-nacos-derby-import.sql`
- 增量升级只认 `upgrades/postgres/`
- 历史脚本全部进 `archive/`

### 3.4 部署目标

正式部署入口固定为：

```text
deploy/
├─ small/
│  ├─ docker-compose.yml
│  ├─ .env.example
│  └─ README.md
├─ medium/
│  ├─ docker-compose.yml
│  ├─ .env.example
│  └─ README.md
├─ full/
│  ├─ docker-compose.yml
│  ├─ .env.example
│  └─ README.md
└─ scripts/
   ├─ deploy-95.sh
   ├─ cleanup-95.sh
   └─ verify-95.sh
```

根目录旧 `docker-compose*.yml` 视为过渡入口，最终应退役，只保留 `deploy/` 作为正式部署入口。

### 3.5 规则目标

规则最终只保留一份总规则文档：

- `docs/06-牛马协作总规则.md`

这份规则文档将统一覆盖：

- 仓库结构规则
- README 维护规则
- 文档维护规则
- SQL 维护规则
- 部署维护规则
- 分支与提交流程规则
- 95 部署与验证规则
- 禁止事项

不再保留一堆单独的治理规则文档作为长期正式结构。

### 3.6 95 环境目标

95 服务器最终结构固定为：

```text
/opt/han/
├─ repo/
│  └─ Han/
├─ deploy/
│  ├─ small/
│  ├─ medium/
│  └─ full/
├─ backups/
│  └─ pre-rebuild/YYYYMMDD-HHMM/
├─ logs/
└─ archive/
```

原则：

- 唯一正式源码目录：`/opt/han/repo/Han`
- 唯一正式部署目录：`/opt/han/deploy/{small,medium,full}`
- 不再允许 `Han-日期`、`canary`、`temp`、`codex` 之类旁路源码目录长期存在
- 不再允许旧 compose 文件混在正式部署目录中

## 5. 执行顺序

### 第一阶段：恢复正式入口

- 恢复 `README.md` 为大文档
- 保留 `docs/index.md` 作为索引
- 停止继续新增碎片化文档

### 第二阶段：合并正式文档

- 将当前 `00-治理`、`01-架构`、`02-开发`、`03-测试`、`04-部署`、`05-运维` 中有效内容合并进 7 份正式大文档
- 将重复内容合并去重
- 将临时过程文档迁入 `archive/`

### 第三阶段：重构 SQL

- 将现有 `tiers/small|medium|full` 下的分模块 SQL 合并成：
  - `small-init.sql`
  - `medium-init.sql`
  - `full-init.sql`
- 保留 Nacos 每档一个导入 SQL
- 保留升级脚本目录
- 历史 SQL 统一归档
- 重新做一次“从零导入”验证

### 第四阶段：收敛部署入口

- 将三档正式部署说明统一到 `deploy/` 与 `03-部署手册.md`
- 将根目录旧 compose 降级为过渡入口
- 后续择机完全退役

### 第五阶段：收敛规则

- 现有治理小文档的有效规则合并进 `06-牛马协作总规则.md`
- 检查脚本同步改成只校验最终目标结构
- 防止以后再次把文档、SQL、部署入口拆碎

### 第六阶段：95 重新收口验证

- 按新目录与新 SQL 结构重新部署
- 做三层验证：
  - 页面级健康回归
  - 主链路回归
  - Full AI 专项回归

## 6. 验收标准

满足以下条件才算整理完成：

- `README.md` 恢复为大文档
- `docs/` 正式文档收敛为少量大手册
- `06-牛马协作总规则.md` 成为唯一正式规则文档
- `sql/tiers/<tier>/` 每档只保留一个大初始化 SQL 和一个 Nacos 导入 SQL
- `sql/archive/` 完整承接历史 SQL
- `deploy/` 成为唯一正式部署入口
- 95 目录结构收敛到目标态
- 新 SQL 在干净环境中可直接导入
- 三档核心功能验证通过

## 7. 当前结论

Han 仓库当前处于“过渡整理态”，并未达到本计划的最终目标。

后续整理将以本计划为准，重点修正以下方向：

- 把 README 从导航页恢复成大入口文档
- 把当前碎片化文档合并成少量大手册
- 把 SQL 从“分模块目录”改成“每档一个大 SQL”
- 把规则从“多份治理文档”改成“一份总规则”

本计划确认后，后续所有整理动作都以这里的目标结构为准，不再回到前一版偏碎的整理方案。
