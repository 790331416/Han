## 2. 背景与目标

开放平台要把校内教育目录能力以受控方式提供给厂商。厂商不是直接拿到一个 URL，而是经过“账号申请、厂商审核、应用创建、接口授权、环境凭证、在线调测、生产审批、运行时鉴权、撤销与审计”的完整闭环。

当前需要解决的核心问题：

1. 接口目录要能说明接口是什么、怎么调用、传什么、返回什么，并支持版本、发布、下线和调测。
2. 授权接口不能脱离接口目录单独维护，否则管理员无法知道授权对象的契约，也无法保证撤销、过期、环境和数据范围一致。
3. 厂商必须先申请并由平台审批，审批通过后才能创建应用和获得授权；厂商账号停用时，应用、凭证和运行时调用必须联动失效。
4. 沙箱和生产必须是两个独立的安全边界，不能用生产凭证调沙箱，也不能以沙箱调测结果替代生产审批。
5. 现有 OAuth2 Bearer Token 和已有开放目录接口必须兼容，旧应用和旧代码无需修改。
6. 所有改动必须遵循 Han 的 A/I/B 分层、租户隔离、审计、结构检查、实库演练、备份和回滚规则。

### 2.1 目标

- 管理端能够维护全局接口目录、版本、OpenAPI Schema、实例和发布状态。
- 厂商能够从登录页申请入驻，查询申请结果，登录门户后自助维护应用和授权申请。
- 平台管理员能够审核厂商、应用生命周期、资源授权和生产开通。
- 运行时对每个开放 API 执行全量 Bearer Token、应用、环境、资源、Scope、数据范围、有效期和厂商状态校验。
- 在线调测只允许调用目录中已发布且允许调测的资源，调测请求落审计记录，不允许服务端代理任意 URL。
- 生产发布有可恢复备份、哈希校验、灰度或分阶段切换、健康检查、接口矩阵和观察窗口。

### 2.2 非目标

- 不引入 WSO2、Gravitee、Apache APISIX 或新的 API Gateway 依赖。
- 不重写现有认证中心，不建立第二套用户、租户或权限系统。
- 不把全局接口目录复制到每个租户，也不因目录可见而自动授予访问权。
- 不在文档、代码、SQL、日志、截图或测试报告中写入凭据和真实数据。
- 不以一次编译成功代替数据库实库验证、浏览器验证或生产业务验收。

## 3. 核心架构决策：页面一体呈现，数据分层存储

### 3.1 为什么不是一张表

接口目录和接口授权在产品页面上应当形成一个连续操作链，但它们回答的是两个不同问题：

| 对象 | 回答的问题 | 典型数据 | 是否按租户 |
|---|---|---|---|
| 接口目录 | 平台提供什么能力，如何调用 | 接口编码、名称、HTTP 方法、路径、Scope、敏感级别、申请/调测开关 | 全局 |
| 接口版本 | 该能力当前哪个契约可用 | 版本号、OpenAPI Schema、入参实例、出参实例、错误实例、认证配置、沙箱配置 | 全局版本 |
| 应用授权申请 | 谁申请了什么权限，为什么申请 | 应用、资源、环境、Scope、数据范围、配额、期限、申请理由、审批结果 | 租户 |
| 生效授权 Grant | 当前谁实际有权调用 | 租户、应用、资源、环境、授权 Scope、数据范围、有效期、状态 | 租户 |
| 应用凭证 | 调用方用什么证明自己 | client_id、凭证哈希、环境、状态、轮换时间、过期时间 | 租户 |
| 调测审计 | 谁在什么时间调过什么 | 应用、厂商、资源、环境、请求摘要、状态码、结果、耗时 | 租户审计 |

如果把目录和授权合成一张表，会产生以下问题：

- 同一个接口被多个厂商、多个应用、多个环境授权时，接口契约重复存储并互相覆盖。
- 目录发布或版本更新会误改已有授权；撤销一个厂商会误下线公共接口。
- 不能表达“同一应用在沙箱有教师读取权限、生产只有设备读取权限”。
- 无法对授权申请、审核、续权、撤销、过期形成独立审计历史。
- 全局目录被租户插件误加租户条件后，管理员和厂商看到的接口不一致。

因此采用“目录定义能力、授权定义关系、凭证定义身份、运行时组合校验”的模型。

### 3.2 页面为什么要一体化

页面不应让用户先记住资源 ID，再跳到另一个无上下文的授权菜单。正确交互是：

1. 打开接口目录。
2. 在目录详情查看接口、请求方式、路径、Scope、版本、OpenAPI Schema、入参实例、出参实例、错误实例、认证要求和沙箱说明。
3. 在同一详情页查看当前应用在 SANDBOX/PROD 的授权状态。
4. 选择应用、环境、Scope、数据范围、配额和有效期，直接提交授权申请。
5. 审批通过后，在同一页面生成对应环境凭证。
6. 点击在线调测，系统只允许调用当前资源和当前环境，并把调测记录写入审计表。

管理员页面可以拆成“接口目录”“厂商”“应用”“授权审批”四个菜单，但它们通过资源详情、应用详情和授权详情互相跳转。厂商门户也应以“接口目录详情 → 申请授权 → 生成凭证 → 调测”为主路径。页面一体化，数据分离，既保持体验连续，又保留安全边界。

### 3.3 目录详情必须包含的字段

目录基础对象至少包含：

- 接口编码、接口名称、分类、HTTP 请求方法、开放路径。
- Scope 编码、描述、敏感级别、负责人。
- 启用/停用状态、草稿/待审核/已发布/已下线状态。
- 是否允许厂商申请、是否允许在线调测。
- 版本列表和当前已发布版本。

版本对象至少包含：

- 版本号。
- OpenAPI Schema。
- 请求示例、成功响应示例、错误响应示例。
- 认证配置、沙箱配置。
- 草稿、已发布、已废弃状态及发布时间、废弃时间。

目录可见不等于可调用。运行时必须同时满足资源启用、资源已发布、Grant 生效、环境匹配、Scope 匹配、数据范围匹配、应用和厂商状态有效。

## 4. 厂商从申请到上线的完整业务流程

### 4.1 流程总览

~~~mermaid
flowchart LR
    A[登录页申请入口] --> B[公开注册\nRSA密文+验证码]
    B --> C[厂商申请待审核]
    C --> D{平台审核}
    D -- 驳回/补充材料 --> B
    D -- 通过 --> E[厂商账号激活]
    E --> F[创建应用]
    F --> G[选择目录资源]
    G --> H[申请沙箱授权]
    H --> I{授权审批}
    I -- 驳回 --> G
    I -- 通过 --> J[生成沙箱凭证]
    J --> K[在线调测与审计]
    K --> L{生产审批}
    L -- 不通过 --> K
    L -- 通过 --> M[生成生产凭证]
    M --> N[生产调用]
    N --> O[轮换/续权/撤销/过期]
~~~

### 4.2 登录页申请入口

登录页增加“厂商入驻申请”和“查询申请进度”入口，入口不直接创建应用，不直接返回 Token，不直接发放接口权限。

公开注册前：

1. 前端调用 GET /auth/vendor/publicKey 获取厂商注册专用 RSA 公钥。
2. 前端使用公钥加密密码；不得把明文密码提交给 auth。
3. 根据验证码开关获取 GET /auth/captcha；若开启，提交 captchaUuid 和 captchaCode。
4. 调用 POST /auth/vendor/register。
5. 页面展示申请编号，不展示凭证、Token 或数据库对象。
6. 通过申请编号和联系电话调用 GET /auth/vendor/application/status 查询申请状态。

公开注册字段按当前 DTO 约束执行：厂商名称、统一社会信用代码、联系人、联系电话、门户账号手机号、联系邮箱、账号邮箱、行业、官网、申请说明、用户名、昵称、RSA 密文密码和验证码字段。手机号、邮箱、社会信用代码、用户名和长度必须在 auth 层再次校验，不能只依赖前端。

### 4.3 厂商审核与账号生命周期

厂商申请通过前：

- 申请记录只表示“申请事实”，不得创建可调用应用和有效凭证。
- 账号可以创建为待激活或受限状态，不能登录后绕过审核。
- 申请编号和联系电话必须同时匹配才能查询公开状态，避免枚举企业申请。

审核通过后：

- 创建或激活厂商主体与申请用户关联。
- 默认授予厂商门户角色，角色只含自服务权限。
- 任何审核、管理员、资源发布和生产开通权限必须由平台管理员角色持有。

厂商状态建议固定为：

| 状态值 | 含义 | 是否允许登录门户 | 是否允许运行时调用 |
|---:|---|---|---|
| 0 | 待提交/初始 | 否 | 否 |
| 1 | 待验证 | 否 | 否 |
| 2 | 待审核 | 否或受限 | 否 |
| 3 | 补充材料 | 否或受限 | 否 |
| 4 | 审核通过 | 是 | 由应用和授权决定 |
| 5 | 审核驳回 | 否 | 否 |
| 6 | 暂停 | 否或仅查询 | 否 |
| 7 | 注销 | 否 | 否 |

申请表状态与厂商主体状态分开保存：申请状态 1 表示待审核，2 表示通过，3 表示驳回；主体状态使用上表的生命周期值。不要用一列同时表达申请和主体。

### 4.4 应用创建和生命周期

应用属于厂商，在租户内隔离。厂商 Owner 可以创建和维护应用，Developer 可以参与调测但不能越权审批，Viewer 只读。

应用生命周期：

| 状态值 | 名称 | 进入条件 | 允许的下一步 |
|---:|---|---|---|
| 0 | 草稿 | 创建应用 | 1 |
| 1 | 待审核 | 提交沙箱申请前的审核节点 | 2 |
| 2 | 沙箱已开通 | 平台批准沙箱 | 3 |
| 3 | 调测中 | 已获得沙箱授权并开始调测 | 4 |
| 4 | 生产待审核 | 厂商提交生产申请且沙箱验收通过 | 5 |
| 5 | 生产已开通 | 平台批准生产 | 6 或 7 |
| 6 | 暂停 | 管理员暂停 | 5 或 7 |
| 7 | 撤销 | 管理员终止 | 不再恢复 |

应用状态启用/停用和生命周期状态是两个维度。停用会阻断运行时；生命周期用于表达审批进程。环境策略 SANDBOX_FIRST、PROD_ONLY、ALL 必须在应用层校验，不能只靠前端下拉框。

### 4.5 从目录详情申请授权

厂商在资源详情页选择：

- 应用。
- 环境：SANDBOX 或 PROD。
- 资源 Scope。
- 数据范围，例如学校 ID 集合或系统允许的数据范围表达式。
- 调用配额。
- 有效期；0 表示永久，其余按天数计算。
- 申请理由。

提交后写入 open_authorization_request，状态为待审核。申请快照必须保留当时的 Scope、数据范围、环境和理由，避免目录后来变化后无法复核申请内容。

审核通过后写入或更新 open_app_resource_grant。Grant 唯一键为：

tenant_id + app_id + resource_id + environment

唯一键不包含状态，撤销或过期后再次申请必须按同一键续权/upsert，不能盲目插入第二行。运行时查询必须同时带租户、应用、资源、环境、状态、有效期和 Scope。

### 4.6 凭证、调测和生产开通

凭证规则：

- SANDBOX 与 PROD 分开生成和轮换。
- client_id 可展示；client_secret 只在生成或轮换成功时展示一次。
- 数据库存储 BCrypt 哈希或等价不可逆摘要，不存明文 secret。
- 轮换先使旧凭证失效，再返回新凭证；旧 Token 由运行时和 Redis 生命周期控制。
- 凭证状态停用、轮换、过期时，不能继续换取 Token。

沙箱调测规则：

1. 应用生命周期至少达到沙箱开通。
2. 资源必须启用、已发布、允许调测。
3. Grant 必须是 SANDBOX 且 Scope、数据范围、有效期均匹配。
4. 调测调用必须使用 SANDBOX 凭证或已批准的沙箱 Token。
5. 服务端不接受任意 URL，不做通用代理；只能根据资源目录映射到已登记路由。
6. 调测结果写入 open_api_test_run，记录结果和耗时，不写入 secret、完整 Token 或敏感业务数据。

生产开通规则：

- 沙箱调测和接口矩阵通过后，厂商提交生产开通申请。
- 平台管理员复核厂商状态、应用信息、生产数据范围、生产凭证、回滚联系人和观察计划。
- 应用生命周期从 4 进入 5 后，才能生成 PROD 凭证并接受生产 Grant。
- 生产调用仍执行与沙箱相同的资源、Scope、数据范围、有效期和状态校验，只是环境为 PROD。

## 5. 角色、权限和租户边界

### 5.1 角色职责

| 角色 | 主要能力 | 明确禁止 |
|---|---|---|
| 平台超级管理员 admin | 厂商审核、资源目录维护和发布、授权审核/撤销、凭证监管、缓存刷新、生产审批 | 不绕过审批直接写运行时 Token |
| 租户管理员 tenantAdmin | 本租户开放平台配置、厂商和应用监管，按实际菜单授权 | 不跨租户查询或审批 |
| 厂商 Owner | 查看所属厂商、创建应用、提交授权、管理本厂商凭证、发起生产申请 | 不审核自己或其他厂商的申请 |
| 厂商 Developer | 查看允许的资源、参与沙箱调测、查看本应用授权 | 不改厂商主体、不生产审批、不看 secret 历史 |
| 厂商 Viewer | 只读查看本厂商、应用、授权和调测 | 不创建、审核、撤销、轮换 |
| 公开申请人 | 注册和按申请编号查询状态 | 不登录门户、不创建应用、不调用开放 API |
| 内部服务账号 | auth 与 han-open 之间调用受保护的内部接口 | 不对公网开放内部路由 |

### 5.2 权限命名建议与当前菜单

管理端权限采用资源化命名：

- 厂商：open:vendor:list、open:vendor:query、open:vendor:review、open:vendor:manage。
- 应用：open:app:list、open:app:query、open:app:add、open:app:edit、open:app:remove、open:app:resetSecret。
- 接口目录：open:api-resource:list、open:api-resource:query、open:api-resource:add、open:api-resource:edit、open:api-resource:remove。
- 授权：open:grant:query、open:grant:apply、open:grant:review、open:grant:revoke。
- 凭证：open:credential:query、open:credential:manage。
- 调测：复用 open:grant:apply 进入本厂商调测提交，查询复用 open:grant:query。
- 管理配置：open:admin:config。

菜单 SQL 只给 admin 角色关联审核菜单；openVendor 角色只关联门户自服务菜单，不授予审核、资源发布或管理员配置权限。菜单权限不是最终安全边界，控制器 PreAuthorize、服务层厂商归属校验、租户过滤和运行时鉴权必须同时存在。

## 6. 状态机与运行时判定

### 6.1 授权申请和 Grant

| 对象 | 状态 | 含义 |
|---|---|---|
| open_authorization_request | 0 | 待审核 |
| open_authorization_request | 1 | 审核通过 |
| open_authorization_request | 2 | 审核驳回 |
| open_app_resource_grant | 0 | 待审核/待生效 |
| open_app_resource_grant | 1 | 已生效 |
| open_app_resource_grant | 2 | 已驳回 |
| open_app_resource_grant | 3 | 已过期（由运行时判定或定时任务归档） |
| open_app_resource_grant | 4 | 已撤销 |

正常路径为：

授权申请 0 → 审核通过 1 → Grant 1 → 到期转 3 或管理员撤销转 4。

异常路径：

- 重复提交同一应用、资源、环境的待审申请必须返回重复申请或复用已有申请。
- 已生效且未过期的 Grant 不允许再次创建冲突授权。
- 已驳回、已过期、已撤销的 Grant 允许按唯一键重新申请或续权。
- 资源下线、厂商停用、应用停用、凭证停用都会在运行时阻断调用。

### 6.2 接口资源和版本

资源状态：

- status：0 启用，1 停用。
- publish_status：0 草稿，1 待审核，2 已发布，3 已下线。

版本状态：

- status：0 草稿，1 已发布，2 已废弃。

一个资源同时只能有一个已发布版本。发布版本前必须校验 OpenAPI Schema 可解析、示例结构合法、路径和方法与资源匹配；发布后刷新 ResourcePathMapping 缓存。下线保留历史版本，不能物理删除历史审计。

### 6.3 运行时鉴权顺序

~~~text
请求进入网关/开放控制器
  → 读取 Bearer Token
  → 校验 Token 有效期、客户端和环境
  → 解析 appId、tenantId、vendorId、environment、scope、dataScope
  → 根据 method + path 命中全局目录和已发布版本
  → 校验资源 status、publishStatus、allowTest/allowApply
  → 查询 tenant + app + resource + environment 的有效 Grant
  → 校验请求 Scope 是 Grant 的子集
  → 校验 schoolId 等数据范围
  → 转换为内部服务调用，禁止暴露内部路由
  → 写入必要审计，不写入凭据和原始 Token
  → 返回业务结果
~~~

缓存只能缓存目录映射和短期权限结果，缓存键必须包含租户、应用、资源、环境、Scope 版本或授权版本；Grant 撤销、凭证轮换、资源发布和厂商停用时必须刷新或失效相关缓存。限流继续复用 Han 现有扩展点，第一版不引入新网关。

### 7.2 数据库一致性原则

- 租户业务表统一 tenant_id NOT NULL；审计列与 BizEntity 对齐。
- 软删除统一 del_flag，不再使用 is_deleted 或 deleted。
- 全局目录表由租户插件排除；open_app、厂商、授权和调测表不能排除租户。
- apply_data、request_data、data_scope 统一 TEXT，应用层使用 Jackson 处理 JSON 字符串，不新增 TypeHandler 依赖。
- Grant 唯一键不含 status，续权按唯一键 upsert。
- MySQL 8.4 使用 information_schema + PREPARE/EXECUTE 的幂等增量写法，不使用 MySQL 不支持的 ADD COLUMN IF NOT EXISTS。
- PostgreSQL 升级脚本进入 sql/upgrades/postgres/，并登记到两套 rehearsal 脚本。

## 9. 全接口测试矩阵

“所有接口测试通过”不是只验证 HTTP 200，而是每个接口都至少覆盖正例、未登录、认证失败、越权、边界、过期/撤销、兼容或恢复路径。测试数据必须使用临时、可清理的厂商、应用、资源和租户，禁止使用真实业务数据。

### 9.1 认证与权限通用矩阵

| 场景 | 预期 |
|---|---|
| 无 Authorization | 401 或项目统一未登录业务码 |
| Authorization 非 Bearer | 401/业务异常，不进入业务服务 |
| Bearer Token 过期 | 401，不能命中内部服务 |
| Token 已撤销 | 401，Redis 和持久化状态均不再认可 |
| client_secret 错误 | Token、SSO、撤销、自省全部拒绝 |
| 资源不存在或未发布 | 404/无权限，不返回内部堆栈 |
| Scope 不足 | 403，不能以同 Scope 访问另一 resource |
| schoolId 超出 dataScope | 403，不能通过空值、重复值或字符串绕过 |
| 环境不一致 | SANDBOX Token 访问 PROD Grant 或反之均拒绝 |
| 应用停用 | 新 Token、运行时调用和调测均拒绝 |
| 厂商暂停/注销 | 厂商下所有应用运行时拒绝 |
| Grant 过期/撤销 | 立即拒绝，缓存失效 |
| 跨租户 appId/resourceId/grantId | 404 或 403，不泄露存在性 |

### 9.2 公开注册和门户矩阵

| 接口族 | 正例 | 负例/边界 |
|---|---|---|
| vendor/publicKey | 获取公钥 | 不得返回私钥；多次请求公钥格式稳定 |
| vendor/register | 合法 RSA 密文、验证码和唯一企业资料提交 | 明文密码、空字段、非法字符、长度超限、重复用户名、重复资质、验证码错、重复提交 |
| application/status | 编号 + 正确联系电话 | 只给编号、电话不匹配、格式异常、过期或不存在编号 |
| login | 审核通过且启用账号登录 | 待审核、停用、锁定、验证码错、密码错、RSA 边界 |
| vendor/my | 所属厂商列表 | 未登录、非成员、停用厂商 |
| vendor/bind-user | Owner/管理员绑定合法用户和角色 | 非法角色、跨租户用户、重复绑定、Viewer 操作 |

| 接口族 | 正例 | 负例/边界 |
|---|---|---|
| resource list/detail | 启用资源列表、管理端含停用资源、详情含版本 | 普通厂商看到停用运行资源、跨租户污染全局目录、排序不稳定 |

|---|---|---|
| OAuth discovery | HTTP 代理头和 HTTPS 代理头下 issuer 正确 | 错误 Host/Proto 不能生成可误导的 issuer |

### 9.5 测试产物和通过标准

每轮测试必须输出：

- 执行命令、提交短 SHA、数据库类型和环境名称。
- 用例编号、接口、输入概要、预期状态、实际状态、响应业务码。
- 失败时的服务日志关联 ID；不记录完整 Token、secret、密码或真实个人数据。
- 测试数据创建和清理记录。
- 未覆盖接口和阻塞项。

通过标准：

- 目录、厂商、应用、授权、凭证、调测、OAuth、SSO、三条运行时目录接口均有正负例。
- 单元/集成/前端构建/浏览器流程无失败。
- 401、403、过期、撤销、跨租户、跨资源、环境越权均实际触发并被断言。
- 任何“只返回 200”但业务码错误、数据为空或安全校验未命中的用例均不算通过。

## 14. 已知风险和发布阻塞

### 14.1 HTTPS 是在线调测前置条件

浏览器在线调测会把访问令牌放入请求授权头，并受到混合内容、证书信任和跨域策略影响。当前若入口仍是 HTTP，只能做 API 层验证，不能把浏览器调测宣布为生产就绪。

上线前必须确认：

- 公开入口使用受信任 HTTPS 证书。
- 网关正确转发 X-Forwarded-Proto、Host 和端口，Discovery 生成的 issuer、token_endpoint、userinfo_endpoint 与实际访问协议一致。
- OpenAPI Console 或调测请求不会从 HTTPS 页面访问 HTTP API。
- CORS、响应头、日志脱敏和浏览器 Network 面板不泄露 Token。
- 证书续期和过期观察有人负责。

### 14.2 auth 单副本与注册 RSA 边界

厂商注册只允许由 han-auth 的公开入口完成 RSA 解密。han-open 不重复解密，不接受明文密码，不保存私钥。GET /auth/vendor/publicKey 返回的公钥必须与处理 POST /auth/vendor/register 的私钥属于同一配置。

在确认所有 auth 副本共享同一受控 RSA 密钥配置前，厂商注册只能路由到单个 auth 副本；不能让多个带不同运行时密钥的 auth 副本随机接收注册请求。上线前必须选择并验证以下一种方案：

1. auth 单副本承接注册，完成限流、注册和审核入库；或
2. 多副本共享同一密钥管理配置，并通过真实注册回归验证负载均衡下每个副本均能解密。

该边界不影响已存在的普通登录 RSA 开关，但两条公钥入口不能混用。测试报告只能记录“公钥获取成功、密文注册成功/失败原因”，不能记录密文、私钥或密码。

### 14.3 旧 OAuth 兼容边界

- 旧的 /open/api/v1/directory/teachers、students、devices 路径和 Bearer 方式保留。
- 既有 open_app 且 vendor_id 为空的旧应用继续走兼容 client credentials/生产路径。
- 新厂商应用优先使用 open_app_credential、Grant、environment、resource 和 Scope 细粒度校验。
- 不恢复 Basic Auth 并行链路，不把旧兼容路径扩展为绕过新资源权限的后门。
- 旧代码无需修改；任何改变返回结构、分页含义、参数名或错误语义的行为必须单独审批和回归。

- [Consumer](https://apisix.apache.org/docs/apisix/terminology/consumer/)：Consumer 与 Credential、Route 和插件组合。
- [Credential](https://apisix.apache.org/docs/apisix/terminology/credential/)：凭证可绑定认证插件，Consumer 可配合限流。

本项目借鉴：把“调用者身份、凭证、资源路由、限流策略”分开建模，并保留流量控制扩展点。差异是当前系统继续由现有 Han 网关和应用服务完成 Bearer、Grant、数据范围和审计校验，不引入 APISIX 运行时。
